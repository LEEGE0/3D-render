## 브랜치

- `main`: 검증된 통합 기준선
- `codex/<작업>`: 기능·문서·조사 작업 브랜치
- 긴 작업은 사용자에게 확인 가능한 작은 마일스톤 커밋으로 나눈다.
- 원격에 같은 목적 브랜치가 있으면 재사용하고 무의미한 중복 브랜치를 만들지 않는다.

현재 원격 저장소가 빈 상태에서 첫 작업 커밋은 `codex/animation-assets-prep`에 생성됐다. 기본 브랜치 통합은 변경 묶음 검토 후 수행한다.

## 커밋 단위

한 커밋은 하나의 리뷰 가능한 목적을 가진다.

- `docs:` 문서와 정책
- `feat:` 사용자 기능
- `fix:` 결함 수정
- `test:` 테스트만 추가·수정
- `refactor:` 동작을 바꾸지 않는 구조 변경
- `build:` 빌드·도구·의존성
- `perf:` 성능 개선
- `chore:` 기타 유지보수

커밋 메시지 본문이 필요하면 변경 이유, 사용자 영향, 검증 명령과 알려진 제한을 적는다. 생성 파일과 외부 바이너리를 실수로 포함하지 않는다.

## 작업 완료 절차

1. `git status --short --branch`로 작업 트리를 확인한다.
2. 변경 파일의 staged/unstaged diff를 검토한다.
3. 작업에 맞는 테스트·빌드·문서 검증을 최신 상태로 실행한다.
4. `git diff --check`로 공백 오류를 확인한다.
5. `git add -- <경로>`로 작업 파일만 스테이징한다.
6. `git diff --cached --name-only`, `--stat`, `--check`를 확인한다.
7. 커밋한다.
8. 현재 브랜치를 원격에 푸시한다.
9. 원격 추적 브랜치와 HEAD가 일치하는지 확인한다.

`git add .`, `git add -A`, `git add --all`과 사용자 요청 없는 강제 푸시는 금지한다.

## 사용자 정상 동작 확인과 태그

사용자가 “잘 된다” 또는 같은 의미를 말해도 바로 태그하지 않는다. 다음과 같이 구체적으로 재확인한다.

> “가이드 V1을 불러온 뒤 탑뷰에서 캐릭터를 이동하면 3D와 저장 결과에도 같은 위치가 반영되는 현재 버전을 정상 동작 버전으로 기록해도 될까요?”

사용자가 긍정적으로 답한 뒤 다음 순서를 수행한다.

1. 해당 시나리오와 관련 자동 검증을 다시 실행한다.
2. 미커밋 변경이 있으면 확인된 경로만 커밋·푸시한다.
3. 태그가 가리킬 정확한 커밋 SHA를 확인한다.
4. 기존 동일 목적 태그가 있는지 확인한다.
5. 주석 태그를 만든다.
6. 태그 하나를 명시해 원격에 푸시한다.

태그 형식:

```text
working/<기능-슬러그>-YYYYMMDD-HHmm
```

태그 메시지에는 다음을 포함한다.

- 정상 동작 기능
- 사용자가 확인한 시나리오
- 테스트 환경
- 관련 제한
- 사용자 재확인 일시

예시 명령:

```powershell
git tag -a "working/dual-view-sync-20260827-1530" <commit-sha> -m "탑뷰/3D 위치 동기화 정상 동작 사용자 확인"
git push origin "working/dual-view-sync-20260827-1530"
```

태그는 이미 공유된 역사 기록이므로 이름을 재사용하거나 임의로 이동하지 않는다. 잘못된 태그는 사용자와 상의해 새 교정 태그를 만들고 기존 기록을 보존한다.

## 릴리스 버전

실행 가능한 배포가 시작되면 의미적 버전 `MAJOR.MINOR.PATCH`를 사용한다.

- MAJOR: 문서·프로젝트 호환성이 깨지는 변경
- MINOR: 하위 호환 기능 추가
- PATCH: 하위 호환 버그 수정

사전 릴리스는 `v0.1.0-alpha.1` 형태를 사용한다. `working/` 태그는 사용자 확인 지점이고 정식 릴리스 태그와 목적이 다르다.

- 알려진 제한과 복구 방법 기록

## 롤백과 수정

공유 브랜치의 기록을 강제로 다시 쓰지 않는다. 문제 커밋은 새 revert 또는 수정 커밋으로 해결한다. 사용자 문서 포맷 결함은 코드 롤백만으로 끝내지 않고 손상 가능성, 복구 도구와 마이그레이션 경로를 함께 검토한다.
